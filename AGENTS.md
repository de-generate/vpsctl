# AGENTS.md

Scripts and docs for bootstrapping and operating a general-purpose Ubuntu Server VPS (24.04 LTS+). See README.md for the overview.

## Conventions

- **Bash, strict mode.** `setup.sh` runs with `set -euo pipefail`; `lib/*.sh` files are sourced, not executed, and have no shebang.
- **One step per file.** `lib/<name>.sh` defines `step_<name>()`. To add a step: create the file, then add it to `STEPS` and `STEP_DESCRIPTIONS` in `setup.sh` (order matters, `ssh` stays last).
- **Idempotent.** Every step must be safe to run again. Write whole config files with `write_file` (starting with `$MANAGED_HEADER`) instead of appending or using `sed` on system files. Prefer drop-in directories (`*.d/`) over editing main configs.
- **App deployment** is split in two: `bin/vps` (client, must stay portable: bash + ssh + tar, runs in Git Bash on Windows) and `bin/vpsctl` (server, does all the work, installed by the `vpsctl` step). Keep the client thin. Caddy routes are generated by vpsctl into `/srv/vps/caddy/etc/sites/`; the base Caddyfile is generated by `lib/caddy.sh`. Validate Caddyfile changes with `caddy validate` / `caddy fmt`.
- **Config** lives in `setup.conf` (git-ignored). Each new option gets a default in `load_config()` and a documented entry in `setup.conf.example`.
- **Never lock the user out.** Anything touching SSH or the firewall must validate first (e.g. `sshd -t`) and keep the current session working.
- **LF line endings** (enforced by `.gitattributes`). The repo is edited on Windows but runs on Linux.
- Keep `docs/` in sync with behavior changes; ideas for later go in `docs/future-improvements.md`.

## Checking changes

There is no test suite. At minimum run `bash -n` on changed scripts and `shellcheck setup.sh lib/*.sh bin/*` if available. Real verification means running against a fresh Ubuntu VM or a throwaway VPS.
